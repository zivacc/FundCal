# 基金搜索加载与延时分析

日期：2026-09-05。结论：延时由首次全量索引加载、过期缓存等待、首次搜索字段预处理，以及列表 SQL 关联放大共同造成；仅缩短输入防抖无法解决。

## 两条不同的搜索链路

计算器、基金详情和净值比较的联想搜索使用浏览器本地索引：

```text
聚焦/输入 → 页面搜索函数 → 共享缓存（内存 → IndexedDB）
                              ↓ 无缓存 / 需要校验
                     /api/fund/search-index
                              ↓ API 失败且无旧缓存
                  data/allfund/search-index.json
                              ↓
                  浏览器匹配、评分、排序、渲染下拉
```

索引含 code/name/initials，当前 API 返回 28,188 条、原始 JSON 2,333,723 字节。基金费率和净值不随搜索索引一起下载。净值比较额外并行加载 159 条指数索引，再合并两种候选。

基金列表在线模式则在每次搜索、筛选、排序和翻页时请求 `/api/fund/list?page=...&q=...`，服务端使用同一套 JS 匹配规则得到代码集合，再交给 SQLite 过滤和分页。该页面不需要先在浏览器下载全量基金索引。

## 已确认的等待点与本批改动

1. 原先冷启动时查询全部基金并生成拼音，后续请求仍查全表。即使是 304，也要先重新序列化全部 JSON 并计算 ETag。现在按 DB 连接保存索引快照、序列化结果、ETag 和 gzip 字节，启动时预热；通过 `data_version` 与 `total_changes()` 检测外部提交和本连接写入后失效。未改变搜索成员范围及字段裁决。
2. 原 API 没有压缩，2.33 MB 响应会放大慢网络下载耗时。现在按 Accept-Encoding 返回约 450 KB gzip，传输体积减少约 81%，并设置 Vary；禁用 gzip 的客户端仍能读取原 JSON。
3. 原共享缓存超过 5 分钟就等待网络完成，实际并非注释描述的 SWR。现在基金和指数搜索启用先读旧数据、后台校验：5 分钟内直接复用；5 分钟至 7 天可先返回副本，后台请求去重。其他数据请求仍默认等待校验。超过 7 天先等待网络；网络失败仍保留原有离线兜底行为。
4. 页面原有额外缓存会一直保留旧数组或一次失败后的空数组。现在计算器和详情复用共享缓存；净值页面只有在底层数组变化时才重新合并。后台更新在下一次搜索时可见。
5. 净值搜索原本等输入后再加载数据。现在三个主要搜索框均支持聚焦预加载；空查询不再遍历并预处理全部条目。计算器原来聚焦也会触发加载，本次将该行为显式化。
6. 列表原 SQL 可能先扫描 fund_meta，再对每行展开匹配代码 JSON，`hs300` 约 600 ms。现在从匹配代码集合开始，固定使用已有的 `idx_fund_meta_code` 查表，保留相关度、筛选和分页。显式来源筛选也验证了代码索引，防止 SQLite 改用 source 索引后重复扫描。

## 实测结果

本机 Node v24.16.0、串行请求，HTTP 时间包含接收完整响应；不是公网延时或浏览器输入到下拉渲染时间。原始记录：[优化前](search-before.json)、[优化后](search-after.json)。

| 项目 | 优化前 | 优化后 |
|---|---:|---:|
| 索引传输体积 | 2,333,723 B | 450,301 B |
| 索引重复请求（200） | 35.0 ms | 8.0–10.6 ms |
| 索引条件请求（304） | 27.6 ms | 0.74 ms |
| 列表 hs300 首次搜索 | 765.6 ms | 75.4 ms |
| 列表 hs300 重复搜索（200） | 646.4 ms | 6.5–8.8 ms |
| 列表 hs300 条件请求（304） | 638.6 ms | 5.6 ms |
| 列表精确代码重复搜索 | 40.5 ms | 5.1–5.8 ms |

服务刚启动即请求索引，本次仍有 **153 ms** 等待，与启动预热重叠；预热并未消除构建成本。第一次搜索还有字段规范化成本，优化前单独测得约 60 ms，后续同数组匹配约 3–6 ms。浏览器输入防抖仍保留计算器 50 ms、净值/详情 150 ms。

同一只读事务内比较旧、新关联方式，7 组查询（第 1/2 页、精确代码、无结果、费率排序、费率范围、来源筛选）的完整结果与总数一致；hs300 SQL 查询加计数从约 619 ms 降到 1.13 ms。测试库覆盖空结果、排序、分页、筛选、数据库更新后的索引失效、gzip/304 及 SWR 刷新。

复测命令（本地 API 启动后）：

```bash
node docs/performance/search-load.mjs
```

## 后续可继续改善的部分

- 本次未做公网 Tunnel、弱网、移动端或完整浏览器输入到渲染测量。首页的同步图表库、外部字体与 Excel 脚本也可能推迟可交互时间，应单独做首屏资源时序分析。
- 首次约 60 ms 的本地字段准备可进一步分批或移入 Worker；当前先保留匹配规则，避免以漏匹配换速度。
- DB 版本失效策略较保守：净值等无关数据写入也会触发索引重建；后续可随数据流水线引入专用元数据 revision。
- API 与静态灾备索引的成员和 DTO 契约差异仍属于后续数据流优化；离线缓存状态也可进一步在产品中说明。
